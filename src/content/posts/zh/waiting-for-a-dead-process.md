## 事情经过

那天中午快一点，编码助手要跑一轮很长的 eval。因为要跑挺久，它用 `nohup` 把任务放到后台，输出写进一个日志文件，然后又起了一个循环盯着这个日志：等任务最后打出 `ALL_DONE`，循环就结束，助手再去读结果。

我去忙别的了。快到三点回来一看，什么都没变，就问了一句：真的还在跑吗？

没有在跑，而且从来就没跑起来过。启动命令里目录名写重了，类似 `evals/evals/run.sh`，shell 报了一句 "No such file or directory"，一秒都不到就退出了。日志里只有这一行，以后也不会再有 `ALL_DONE`。等待循环对着一个不会再有人写的文件，查了将近两个小时。

好在没有别的损失。任务根本没启动，一分钱也没花。助手改好路径，一分钟后重新启动了。

## 问题在哪

等待循环默认了一件事：**没看到结束标记，就说明任务还在跑。**这只在任务进程还活着的时候成立。一个后台任务的结局有三种：正常跑完并写出标记；跑到一半崩了，没来得及写；压根没启动起来。只查标记的循环，只能分辨第一种和"还没好"。后两种在它看来和"还没好"一模一样，而且会一直这样下去。

这其实不算 Agent 特有的毛病，人也经常这么写，比如 `tail -f` 盯着日志，或者 `until grep -q DONE log; do sleep 60; done`。区别是人写了这种循环，过二十分钟看日志一直没动，自己就会起疑心。助手不会不耐烦，就一直等下去了。

## 怎么改的

现在等待循环每一轮按顺序查三件事：

1. **结束标记有没有出现？**有就说明跑完了，去读结果。
2. **任务进程还在不在？**进程没了、标记也没有，说明中途挂了。停下来，把日志最后几行打出来。
3. **有没有超过截止时间？**进程还在，但跑的时间远远超出预期，也停下来，交给人去看。

```sh
# 改之前：任务挂了就会一直等下去
until grep -q ALL_DONE run.log; do sleep 60; done

# 改之后：先看标记，再看进程，最后看截止时间
nohup ./run.sh > run.log 2>&1 &
pid=$!
deadline=$(( $(date +%s) + 3*3600 ))
while ! grep -q ALL_DONE run.log; do
  if ! kill -0 "$pid" 2>/dev/null; then
    echo "任务已退出，但没有 ALL_DONE"; tail -20 run.log; exit 1
  fi
  if [ "$(date +%s)" -gt "$deadline" ]; then
    echo "跑了 3 小时还没结束，需要人看一下"; exit 2
  fi
  sleep 60
done
```

`kill -0` 不会给进程发任何信号，只是问一下这个进程还在不在。关键是启动完马上用 `$!` 把 pid 记下来，等待循环要靠它判断，事后再想找就难了。按这个写法，目录名写重的问题第一轮检查就会暴露，也就是第 1 分钟，不用等两个小时。

现在助手启动后台任务都按这个来：启动时记下 pid，每一轮检查都确认进程还在，再按预计时长设一个截止时间。

## 对比

| | 只查结束标记 | 标记 + 进程 + 截止时间 |
|---|---|---|
| 任务正常跑完 | 能发现 | 能发现 |
| 跑到一半崩了 | 一直等 | 下一轮发现，打出日志 |
| 根本没启动 | 一直等 | 第一轮就发现 |
| 卡住不动 | 一直等 | 到截止时间停下 |
| 靠什么发现问题 | 等人想起来问 | 不需要人盯 |
