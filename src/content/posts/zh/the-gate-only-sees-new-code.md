## 事情经过

之前写过一篇[为什么我们要求新代码覆盖率必须 100%](/zh/posts/one-hundred-percent-on-purpose/)。这条规矩我现在还在用。这篇讲的是它管不到的地方。

我们把一个老 Java 服务升级到 Java 25。PR 改动不大：构建文件、基础镜像，再加几处 API 调整。PR 上的质量门禁是绿的：新代码覆盖率 100%，新增问题 0，几千个测试全过。合并，部署，也都没出问题。

过了一会儿有人去看主分支的分析报告，上面有 63 个问题，没有一个在这次 PR 改过的代码里。

## 这 63 个问题是哪来的

升级 Java 版本时，静态分析也会启用针对新版本写的规则。其中三条规则在老代码里报了问题：

- 51 处：参数从来没用过，新版本 Java 允许直接写成 `_`
- 11 处：没用到的局部变量，规则更新后开始报
- 1 处：调用了一个新版本里标记为"将被移除"的 API

这些都不危险，而且在代码里放了好几年，只是都不在这次的 diff 里。PR 门禁只看**新代码**，也就是这次改动新增或修改的那些行。新代码 100% 之所以合理，正是因为每个人只对自己写的代码负责。但反过来，像升级语言版本这种会改变整个代码库评判标准的改动，门禁也只看它改了的那几行。

## 问题出在哪

我把"门禁是绿的"当成了"分支是干净的"。平常改功能的时候，这两件事差不多是一回事。但工具链有变化的时候就不是了，比如升级语言版本、升级分析工具、换规则集。这类改动本身只改几行，却改了所有代码的评判标准。

于是我们单独提了一个小 PR 来清理：51 个参数改名，删掉 11 个变量，换掉那个要被移除的 API。标准还是一样，PR 门禁要绿，测试要全过，然后合并。

## 清理完了，报告上还是 63

合并以后，主分支的报告还是显示 63。

有那么几分钟，我们以为清理没起作用。其实起作用了。当时有两个 PR 前后几分钟进了主分支：先是一个不相关的功能，紧接着是这次清理。每次合并都会在主分支上启动一条流水线。清理那条先跑完，报了 0。几分钟后，前一条流水线也跑完了，它分析的是更早的那个提交，报的是 63。报告页面上显示的，就是最后一个跑完的结果。

我们在主分支最新的提交上重跑了一次分析，结果是 0。报告上那个 63 对旧提交来说没错，只是不是现在的状态。

## 对比

| | 我原来以为 | 实际情况 |
|---|---|---|
| 升级后 PR 门禁是绿的 | 分支是干净的 | 改过的那几行是干净的 |
| 新规则在老代码里报的问题谁来发现 | 门禁 | 去看整个分支的人 |
| 两个 PR 连着合并后的报告 | 对应最新的提交 | 对应最后跑完的那次分析 |
| 什么时候能信报告上的数字 | 报告上有就能信 | 先确认它对应的是哪个提交 |

## 经验

从这件事里我养成了两个习惯。

第一，只要工具链有变化，就去看主分支整个分支的分析结果，不能只看 PR 门禁。新规则要是在老代码里查出问题，马上单独提一个 PR 清理掉，趁着大家对这次升级还有印象。

第二，信报告上的数字之前，先看它对应的是哪个提交。

新代码 100% 这条规矩还是对的。它让每次改动都经得起检查，又不用每个人去还历史欠账。只是有一类改动它管不到：那种会重新定义"历史代码合不合格"的改动。

<div class="callout">
<p><strong>经验：</strong>新代码门禁只检查你改了哪些行，不检查你改了什么标准。升级语言版本、分析工具或规则集之后，要去看整个分支的分析结果。报告上的数字，要先确认它对应的是哪个提交，因为最后跑完的那次分析会覆盖前面的。</p>
</div>
