## 一次事故

一个负责评审需求文档的 Agent，要去找它该评审的文档。搜索条件写得太宽，它匹配到了一份不相关的旧草稿，然后把那份草稿改名成了它本该找的文档名。修复很简单，改一行搜索条件。但那份被改错名字的文档在系统里放了好几天，没人发现，因为系统里没有任何标记能区分"这个名字是 Agent 改的"和"这个名字是人改的"。

这件事的要点是：Agent 没有做任何越权的操作。它有权限改文档名，它改了，改完立刻生效。问题不在权限，在于写进去的东西马上就被当成了事实。

## 两种常见做法，各有问题

Agent 要往别人依赖的系统里写东西，通常有两种反应。

一种是收回权限，让 Agent 只输出建议，由人复制粘贴。安全，但 Agent 变成了一个很慢的自动补全，省下来的时间全花在复制上。

另一种是保留权限，把 prompt 写严：加规则，加例子，写"绝对不能做 X"。这在大多数情况下有效，但极端情况下会失效，而出事的恰恰是极端情况。

这两种做法都默认了一件事：Agent 写进去的东西就是最终结果。我们后来的做法就是打破这个默认。

## 我们的做法：区分"存在"和"生效"

任何共享系统其实都有两层，平时被当成一层。一层是数据存在：一行记录、一个文件、一张工单、一条消息。另一层是数据生效：报表读它，流水线跑它，团队照它行动，频道推给两百个人看。

我们把这两层分开：Agent 可以让数据存在，只有人能让数据生效。实现上就是在数据上加一个状态字段，加上每个下游默认过滤：草稿记录不进报表，草稿 PR 不触发评审，草稿消息留在私有频道。

这个做法在大多数系统里本来就有对应的机制，只是没有用起来：

| 写什么 | 草稿态是什么 | 人怎么确认 | 谁会忽略草稿 |
|---|---|---|---|
| 代码改动 | draft PR，不指定 reviewer；测试没过的加 DO NOT MERGE | reviewer 点 ready | 评审队列、合并机器人 |
| 工单 | Agent 写进自己的字段，不覆盖人写的描述 | 人合并进描述，或忽略 | 读工单的人能看出谁写的 |
| 文档 | 建议模式，不直接改正文 | 文档负责人接受 | 发布版本 |
| 数据记录 | 状态标为"未评审"，归属标为 Agent | 人改状态、接过归属 | 报表默认排除该状态 |
| 消息 | 发到私有频道或 thread | 人转发到团队频道 | 读者 |

每一行只需要两个决定：哪个字段表示草稿；Agent 不碰能把草稿变成生效的那两个字段。

## 一条后来放宽的规则

最能说明问题的例子，是一个往团队测试管理工具里创建测试用例的 Agent。这个工具是团队覆盖率数字的来源，写错一条，图表上的数字就是错的，而团队是照着图表做决策的。

第一版规则很直接：Agent 可以往已有分组里加用例，不能新建分组。安全。但真实用户用了一周，到处碰到"没有匹配的分组，请找人处理"。最需要帮助的场景，恰好被规则挡住了。

后来我们把规则改了。Agent 可以新建分组，但新建的分组默认带报表会忽略的那个状态，归属字段写 Agent 自己。它不会把状态改成"就绪"，也不会改归属，这两个动作留给人，每个只要点一下。这样一改，覆盖率数字完全没受影响，Agent 能处理的场景却多了一大块。

## 配套的三个习惯

只有草稿态还不够，我们还加了三条：

1. **写之前先列清单。** Agent 把要创建的所有记录先列出来，人看一眼，回一个词放行，或一个词全部取消。事后审两百条草稿没人做得到，事前审一张十几行的清单可以。
2. **写完读回来对比。** 每次写入后把记录取回来，逐字段和原意对比。工具偶尔会出错，一条和批准内容不一致的草稿比没有草稿更麻烦。
3. **打上来源标记。** Agent 创建的每条记录都带一个"由 Agent 创建"的标记，放在没人会去改的字段里。几个月后有人问"这条哪来的"，看记录就知道。

## 代价

草稿要有人处理。一个堆满没人看的 Agent 草稿的系统，是另一种垃圾，而且比空的更麻烦。所以我们定了对应的规则：Agent 不确认，人必须要么确认、要么删除，一个 sprint 内没人处理的草稿直接清掉。
