## 背景

刚开始做 Agent 的时候，我对它的理解就是一个循环：调一次模型，看回答，决定下一步，再调一次。后来一年里，同一类系统我用三种方式做了三遍。回头看，每换一次方式，我自己要写的东西都少了一大块。

## 第一种：围着 API 自己写循环

第一套系统是放在 Slack 里的几个助手，分别负责读文档、写方案、改代码。它们看起来是几个不同的机器人，底层其实是同一套代码：通过 Bedrock API 调一次 Claude，外面包一层我们自己写的逻辑。

这里的关键是模型没有状态。它两次调用之间什么都不记得，不会自己调工具，也不知道什么时候该停。这些事全得我们自己写：

- 把对话存下来，下一轮调用时再带上，模型才知道前面说了什么
- 解析模型的回答，判断它想调哪个工具，替它调
- 工具会失败，模型会超时，所以要有队列和重试
- 还要有一个判断"是不是做完了"的逻辑，不然循环停不下来

半年之后，仓库里大部分代码都是这一层，助手真正干活的逻辑反而很薄。系统能用，大家每天也在用，但每加一个新功能都要经过这层我们自己写的 runtime。这层东西，当初谁都没打算专门去做。

## 第二种：迁到托管的 runtime

第二版我们把循环从自己的代码里拿掉了，整体迁到 Bedrock AgentCore。之前手写的那些部分，会话、记忆、工具调用、身份、重启后能接着跑的长任务，都由 AgentCore 负责。我们只需要提供三样东西：指令，工具定义，以及几条"什么时候应该停下来问人"的规则。

改完以后，diff 里最明显的是 runtime 目录基本清空了。

但工作量并没有真的减少，只是换了地方。循环没得调了，整个系统好不好用就取决于两件事：指令写得清楚不清楚，工具契约可靠不可靠。举个例子，有个工具声明"返回工单详情"，但偶尔只返回一个带 key 的空对象。以前这算管道层的 bug，改一下解析就行。现在它变成了 Agent 判断错误，因为 Agent 会拿着那个空对象继续往下推理。

代价是多了一层别人的抽象。出问题要透过 AWS 的接口去排查，状态也存在 AWS 那边。如果循环本身不是你产品的核心，这个交换是值得的。对我们来说确实不是核心。

## 第三种：做成插件，只有几个文本文件

第三种是我之前没想到的。

一个帮工程师写测试的 Agent，我们没有部署成服务，而是做成了 Claude Code 插件，直接跑在开发者本来就开着的编码助手里。没有服务器，没有队列。整个 Agent 就是一个文件夹，里面是几个 markdown 文件写的指令，一份它可以调用的 MCP 工具清单，再加一两个脚本。runtime 是用户笔记本上的 Claude Code，凭据用的是用户自己的。

这样"部署"这件事就变了：发新版本就是在插件 marketplace 里升一个版本号。权限也不用单独申请，用户有什么权限它就有什么权限。而且因为用户就在旁边，Agent 每次要往共享系统里写东西之前，可以先停下来问一句"这样改可以吗"。对共享系统来说，这正是我们想要的。

它的限制也很清楚：不会在夜里自动跑，不会自己去领工单。它能做多少事，取决于有没有人在对话里推它。

## 三种做法对比

| | 自己写循环 | 托管 runtime | 插件 |
|---|---|---|---|
| 例子 | Bedrock API + 自己的代码 | Bedrock AgentCore | Claude Code 插件 |
| 循环由谁跑 | 自己的代码 | runtime | 用户本地的助手 |
| 状态存在哪 | 自己的数据库 | runtime 的存储 | 对话本身 |
| 自己要写什么 | 代码 | 指令 + 工具契约 | 指令 + 工具契约 + 几个脚本 |
| 怎么发布 | 部署一个服务 | 更新指令 | 升版本号 |
| 用谁的凭据 | 服务账号 | 服务账号或 runtime 的身份 | 用户本人 |
| 能不能无人值守 | 能，要自己实现 | 能 | 不能 |
| 人能不能逐步确认 | 要自己实现 | runtime 支持暂停才行 | 默认就是这样 |
| 适合什么 | 一次性转换，没有需要保存的状态 | 在共享频道里自主运行的任务 | 每一步都需要人来决定的工作 |

## 三次都没变的部分

把三次放在一起看，我自己写的东西一次比一次少，形式上也从代码变成配置，再变成指令。指令和工具契约这两样，三次迁移基本原样搬了过去，因为它们一直是纯文本，不依赖任何一种 runtime。

<div class="callout">
<p><strong>现在我怎么选：</strong>先把 Agent 要做的事写成文本，最后再决定用哪种 runtime。需要没人盯着也能跑、发生在共享频道里的任务，用托管 runtime；每一步都需要人决定的工作，放到用户本来就在用的工具里；一次性转换、没有值得保存的状态，直接写个循环就够了。</p>
</div>
