## 事情是这样的

我们给一个 Agent 新写了一个技能，跑 eval。最小的模型三次都是 0.33 分，两个大一点的模型三次都是 0.67 分。

按常规思路，这时候该去改技能的说明了：小模型分低，就多写点指引。

改之前我先把三次运行的 transcript 打开看了一遍。三次 Agent 都把事情做对了：数量对，选的行对，要跳过哪些也列清楚了，还说明了有一个集成没接上，然后停下来等用户确认。有一次它甚至先去检查了一下网络。三次都做对了，三次都没及格。

## 分是在哪里丢的

这个 eval 有三个评分器，其中两个写错了。

第一个是正则。它要求回复里出现测试数据里那个示例邮箱。可是 eval harness 是以真实用户的身份运行的，所以 Agent 每次用的都是用户自己的真实邮箱，还会说一句"发到你自己的邮箱"。Agent 做得没错，是正则写错了。

第二个是 LLM 评委加评分标准。标准里写着：回复必须说明某个工具服务器不可用。但 harness 里给这个服务器准备了一个 mock，它是可用的，Agent 也如实说了可用。评分标准是照着生产环境写的，没考虑测试实际跑在什么环境里。

两个大模型之所以多拿了分，是因为它们照抄了示例邮箱，正则那一项过了；评分标准那一项一样没过。

过了两天，另一个技能也走同样的流程，又碰上了评分器的问题，这次是两个新问题：

- 有个正则用 `(?i)` 做不区分大小写的匹配。这是 Python 的写法，harness 用的是 JavaScript 的正则，`(?i)` 在 JS 里不合法，所以这个评分器每一次运行都直接报错。Agent 不管写什么都不可能通过。
- 有个评分标准很长，列了五六条，要求全部出现才算过，评委又是最小的模型。最大的那个模型给的回复每一条都有，同一个回复让评委判了三次：不过，不过，过。

## 有一个是真 bug

也不是每个失败都怪评分器。有一个请求，技能里没有任何能匹配上的情况，按设计应该直接拒绝。但用户在请求里要求了，小模型就照着去跑了一次检查。这一项评分器判得对，问题在技能本身。改法是在技能里加一句话：匹配不上就停，不管用户怎么说。

如果我一开始就去改技能，这个真 bug 会被另外四个假失败盖住。我很可能还会为了"修好"那四个，让 Agent 去照抄示例邮箱，明明服务器在也说不在。

## 怎么改的

<figure>
<a href="/img/grader/triage.zh.svg" target="_blank" rel="noopener"><img src="/img/grader/triage.zh.svg" alt="排查流程。eval 失败后，先看 transcript。Agent 做对了，就改评分器再跑；Agent 做错了，就改技能再跑。改之前三次都是 0.33，改了评分器之后三次都是 1.0。"></a>
<figcaption>顺序很重要：先看 transcript，再判断是哪一边出了问题。</figcaption>
</figure>

评分器按 harness 实际的运行方式重写了：

- 邮箱的正则，示例邮箱和"你自己的邮箱"两种写法都认。
- 评分标准只要求测试里真正能观察到的东西：没接上的集成必须点名；mock 的那个服务器，说可用、说不可用都行，只要说清楚是哪种。
- 不区分大小写改成 `[Dd][Rr][Aa][Ff][Tt]` 这种写法，什么正则方言都能用。
- 长的评分标准改成一句简短的通过条件。两种回答都对的地方，直接写明"两种都算过"。

Agent 的行为一点没改，小模型从 0.33 变成了 1.0，三次都是。两个大模型也都到了 1.0。那个真 bug 加了一句话之后也没再出现。

## 两种做法的对比

| | 先改 Agent | 先看 transcript |
|---|---|---|
| 怎么理解分数 | Agent 不够好 | 一个需要查清楚的问题 |
| 假失败 | 被"修"进了 Agent 的行为里 | 在评分器里改掉 |
| 那个真 bug | 混在一堆假失败里看不出来 | 找到了，一句话改好 |
| 代价 | 一开始省事，技能越改越差 | 每个失败的运行多花几分钟看 |

## 经验

评分器也是代码。它们通常写得很快，写的人就是写技能的人，而且常常是照着一个跟 eval 实际运行环境不太一样的环境写的。它们会出 bug，跟被测的东西一样。eval 分数只能说明评分器和 Agent 意见不一致，说明不了是谁错了。
