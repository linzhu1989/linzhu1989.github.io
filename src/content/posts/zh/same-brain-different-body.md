## 两个请求

相隔一周，来了两个要同一件事的请求。

一个来自终端前的工程师："帮这个 ticket 规划测试。"他想看到方案，跟它讨论几轮，然后批准。另一个来自晚上六点聊天 thread 里的经理："明早之前把测试规划好。"没有人会盯着它跑。

同一个技能，同样的指令、同样的工具、同样的输出格式。我当时觉得区别只在触发方式。这个判断让我们之后两个月处理了一堆零零碎碎的 bug，每个看起来都是独立的，直到把它们放在一起才看出规律。

## 场景一换，三件事跟着变

技能本身可以共享，就是那份 markdown 指令：读什么、决定什么、产出什么。它在不同 runtime 之间几乎可以原样迁移。但技能周围的环境，从有人在的对话换成没人在的定时任务，有三件事完全不同：

- **谁在看。** 终端里，用户逐行读输出。定时任务里，最早也要等到早上才有人看。
- **能不能问。** 对话里问一句很便宜。凌晨三点的任务里问一句，这一轮就白跑了。
- **什么叫做完。** 终端里用户说完就完。没人在的时候，"完"必须是系统能自己验证的状态。

## 对话场景里出的问题

这边的 bug 有一个共同原因：把对话当成了批处理。

**问题一个一个地问。** 一个评审 Agent 问一个追问，等回答，再问一个，再等，再问第三个。每个问题单独看都合理，合在一起用户体验很差。后来定的规则是：把剩下的问题一次全部问完，已经回答过的不再问。

**状态提示和实际情况不一致。** 有用户反馈编码 Agent 卡了一个半小时，实际 94 秒就跑完了，只是最后那条消息发送失败，屏幕上的"仍在运行"没人更新。另一次，界面显示"尚未开始，请批准"，任务其实已经跑了四分钟，用户再批准一次，同一个任务花了两份钱。在对话里，用户能看到的只有状态提示，提示错了，用户的操作就跟着错。

**默默地猜。** 一个 thread 里提到两张工单，Agent 选了一张，没说。第一版修法是让模型判断用户指的是哪张，被否了。第二版是停下来问用户，结果因为 thread 历史从不重置，一条很早的提及会让这个 thread 永久卡在提问上。最后上线的做法是保留原来的规则，但每次把选中的工单写在回复第一行。在有人逐条读回复的场景里，说清楚比防住更有效。

## 定时任务场景里出的问题

这边的 bug 原因反过来：把无人值守的任务当成了对话。

**每次运行都接着上一次的对话。** 一个夜间 Agent 每晚汇报"这是第四次因同一原因失败"。我们清了它的记忆，第二天它还这么说。查下去发现，传给 runtime 的会话标识符每次运行都一样，它根本不是在"记忆"，而是一周来一直在同一场对话里。对话场景里，长对话是好事；定时任务里，每次运行必须干净开始，需要持久化的身份用另一个专门的 key 保存。

**等一个不在的人。** "可以继续吗？"这种确认在有人的时候是对的。没人的时候，同一个确认会让任务挂到早上。定时任务不能提问，所以要用另一种安全措施：只写草稿，不做最终确认，人早上来审。

**出错不报。** 一个工具返回零条结果，Agent 用通用知识作答，答得很自信，也是错的。对话里会有人说"我问的不是这个"，夜里没有，错误答案直接进了报告。定时任务需要的默认设置是：空结果算错误，缺输入就停，失败发到人第一眼会看到的地方。

## 两种场景对比

| | 对话里 | 定时任务里 |
|---|---|---|
| 谁在看 | 用户，实时 | 没人，要等 |
| 能不能问 | 能，但要一次问完 | 不能，缺什么就停 |
| 安全措施 | 每次写入前确认 | 只写草稿，Agent 不确认 |
| 会话 | 一场长对话 | 每次运行新会话，身份用单独的 key |
| 状态提示 | 必须和实际一致，选择要说出来 | 结果和失败发到人会看的地方 |
| 工具返回空 | 问用户，或说明 | 当作错误 |
| 什么叫做完 | 用户说完 | 系统可以验证的状态 |
| 合适的 runtime | 用户本地的助手 | 托管 runtime 或调度器 |

## 怎么选

拿到一个新技能，我先问一个问题：这件事是不是每一步都需要人决定？是，就做成对话形式，放到用户本来就在用的工具里。如果价值恰恰在于没人的时候也能跑，就做成定时任务，接受它不能提问。

然后为这个场景单独写运行规则，不从另一个场景复制。技能是共享的，规则不是。

<div class="callout">
<p><strong>经验：</strong>技能可以在场景之间迁移，运行规则不能。把技能挪到新场景之前，把提问、状态、会话、失败这四条规则按新场景重写，然后在没人盯着的情况下跑一次，看它怎么失败。</p>
