## 回来第一天看到什么

三周产假，不开电脑的那种。

回来第一个早上，产品看着没变：同一个聊天界面，同一批助手，同样的名字。底下变了。二十来个已经合并的变更把后端换了一套：

- 我之前写过的那个自己维护的循环没了，Agent 全跑在托管 runtime 上，每个 Agent 是一份配置加一份人设文件
- 指令从应用仓库搬出去了，共享仓库成了唯一的存放地
- 每个 Agent 和每个集成之间多了一个共享的 tools server
- 指令文件的正文改成按需加载，不再每轮全部注入

每一项都是同事做的，都有理由。只是这些理由我一条都不知道。

## 为什么读 commit log 不够

我第一反应和每次休假回来一样：读 change log，扫一遍合并的 MR，中午前开始处理工单。这套办法我用了很多年，一直有效。

它有效的前提是变更是叠加的：多了一个功能，改了一个 bug。这次不是，是系统换了结构。commit message 能告诉你什么东西挪到了哪里，不会告诉你作者现在默认了什么。而回来的人会栽的地方，恰恰是那些新的默认。

## 第一天我做了什么

我把整个第一天都花在补课上，一张工单没碰。

**每个变更问四个问题，写下来。** 这是什么？为什么做？替掉了什么？如果我还按旧的理解去做事，会在哪里出错？前三个问题 MR 里都有答案，第四个哪里都没有，得自己想。它也是最值钱的一个。

**从零复现本地环境。** 不是"我机器上能跑，因为以前能跑"，而是干净 checkout，只按仓库里的文档一步步来，直到一个 Agent 在本地回答我。文档漏掉或写错的每一处，都是我的理解会出错的地方。

**画出来。** 一天结束的时候，我能在白板上画出整个系统。这是我判断"补上了"的标准。画不出来，读多少 commit 都不算。

## 一个只有这么做才会发现的 bug

第四个问题真的有回报。

老 runtime 下，指令文件每次都整个注入。大家也就这么写：顶上一段简短描述，真正的规则写在下面，有时很靠下。新 runtime 改成了描述永远加载，正文只在模型觉得需要时才读。这一改，所有写在正文里的规则一下子都变成了"可能被读到"，没有报错，也没有提示。文件一个字没改，改的是"什么一定会被读到"这个前提。

<figure>
<a href="/img/back-from-leave/guaranteed.zh.svg" target="_blank" rel="noopener"><img src="/img/back-from-leave/guaranteed.zh.svg" alt="两种加载模型。旧的：整个指令文件每轮注入，靠下的硬规则一定被读到。新的：只有简短描述永远加载，正文按需取，同一条硬规则现在只是「可用」，经常根本没被读。修法是把承重的规则挪进永远加载的那层，把描述改成决定性的路由。"></a>
<figcaption>同一条规则，在旧 runtime 下一定被读到，在新 runtime 下只是"可能被读到"。</figcaption>
</figure>

change log 里这一条写的是"技能正文渐进式加载"。准确，而且听着像是个优化。如果我不是一上午都在问"按旧的理解会在哪里出错"，不会想到"哪些规则现在变成可选了"这个问题。

问题一说出来，修法就直接了：把承重的规则提到永远加载的那一层，把每段描述改成明确的路由，告诉模型什么时候该读正文。一周后我和同事用一句埋进技能的测试文字验证了共享仓库确实跨两个产品生效：第二天两边都能看到。

## 读 log 和重建理解，差在哪

| | 读 change log | 重建理解 |
|---|---|---|
| 时间 | 一小时 | 一天 |
| 学到 | 什么东西挪了 | 现在默认了什么 |
| 适合 | 叠加式变更 | 结构性变更 |
| 看不到的 | 没变但含义变了的东西 | 基本没有，前提是能画出来 |
| 怎么验证 | 列表读完 | 能把每个决定讲给别人听 |

<div class="callout">
<p><strong>经验：</strong>你不在的时候系统换了结构，回来先花一整天补课：每个变更问四个问题，从零复现环境，能在白板上画出来才算补完。另外，文本底下的加载机制一变，就要查一遍哪些内容是"一定会读到"，哪些只是"可能读到"。</p>
