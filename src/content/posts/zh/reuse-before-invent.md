## 开工时的清单

第二个 Agent 开工那天，我列了它需要的东西：

- 能访问工单系统、wiki 和代码托管
- 指令要有地方放
- 要能发布给别人安装
- 要能开 PR
- 要能读团队的测试管理工具和覆盖率数据
- 生成的测试要有仓库可以放

六项。每一项，公司里都已经有人在维护一个。问题只有一个：给新产品单独做一套，还是搬进已有的那套？

我们六项都搬进去了。九周上线。

## 为什么"另建一套"看起来更好

给新产品画架构图的时候，最自然的画法是自己一列：自己的集成层、自己的仓库、自己的发布流水线，整整齐齐立在已有系统旁边。每个框都归自己管，做什么都不会影响别人。

但每个框也都是一个要运维的系统。要申请凭据，要配监控，坏了要有人接，底下的东西一动就要迁移。而且这一列和已有的那一列功能重复，任何改进要么做两遍，要么不做。

## 六项分别用了什么

| 需要 | 没做的 | 用了什么 | 自己写了什么 |
|---|---|---|---|
| 访问工单、wiki、代码 | 自己的连接器 | 第一个 Agent 已经在用的集成网关，通过 MCP 暴露 | 指令里的工具名 |
| 放指令 | 自己的仓库 | 共享技能库，和其他 Agent 的技能放在同一个目录 | 几份 markdown |
| 发布 | 自己的流水线 | 一个已有插件和它的 marketplace，作为新增的一组命令 | 一个版本号和一条 changelog |
| 开 PR | 一个 PR 步骤 | 插件里已有的建 PR 技能 | 零行 |
| 测试用例和覆盖率 | 自己的存储 | 团队的测试管理工具，以及它前面的服务 | 什么时候调哪个工具的说明 |
| 测试落地 | 新仓库 | 团队已有的两个自动化仓库 | 按仓库规范写的测试 |

第四行值得单独说。让 Agent 开一个 PR 听着简单，实际要处理分支命名、识别远端、找 reviewer、扫密钥、API 拒绝时的手动兜底。插件里已经有一个技能把这些全做了，我们告诉 Agent 去调它，就完了。

第二行有个额外收获。技能放在共享库里，另一个跑在完全不同 runtime 上的 Agent 也能读到同一批文件。我们做了个验证：在某个技能里加一句话，第二天两个产品都能看到。复用是真的发生了，不是画在 PPT 上。

## 用现成的要付什么代价

用别人的东西，就要守别人的规矩。

改一个技能要两个 MR：一个进共享库，一个把副本同步进插件，然后等发布。我们的脚本要能在宿主承诺支持的最老版本 Python 上跑，比我笔记本上的老，这件事是发布当晚才发现的。命名按宿主的规范。发布节奏也是宿主的。这个月 marketplace 换了地方，我们跟着搬，通知用户重装。

这些都是成本，但和自己维护六个系统比，每一项都不算什么。

## 换来了什么

从第一张工单到别的团队能安装，九周，两个人。几乎没有属于我们自己的、会半夜报警的基础设施。

还有一件事后才看出来的好处：因为我们自己写的全是文本，Agent 在几个地方之间搬来搬去几乎不用改。插件换 marketplace 那次，指令一个字没动，用户拿到的是四行命令。拥有得少，和搬得动，是一回事。

## 什么时候还是得自己做

三种情况：

1. 现有系统的负责人说不行，或者不能按你的时间表改。这种依赖你迟早会绕开，不如一开始就想清楚。
2. 你的用量会影响到现有系统。一个夜间任务持续打一个按交互流量设计的网关，那不是复用，是给人添麻烦。
3. 现有系统的抽象和你的场景冲突了三次。我们有过一个 bug，两个月内出现三次，每次看着都不一样，最后发现是共享组件里同一条兜底路径不适合我们的情况。修法是上游把兜底改一次，不是下游再加第四个特例。上游改不了，那就自己做。但先数到三。
