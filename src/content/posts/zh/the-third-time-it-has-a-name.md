## 三起事故

第一起很小。聊天 thread 里一条回复被吞了：Agent 读了消息，判断不是它会处理的类型，就没有回应。我们往路由表里加了这个 case。修好了。

第二起看起来是另一类问题。一个评审 Agent 被要求重新看一份上周评审过的文档。它没有重读，而是用很具体、很自信的理由捍卫上次的结论，而那些理由指向的内容文档里已经删掉了。我们加了一条规则：重新评审必须重新拉文档。修好了。

第三起又是另一种。一个工程 Agent 回答代码问题，给出的文件路径和函数名根本不存在，两次，两次编的还是同一批名字。我们明明有代码搜索工具就是做这个的，它没调。正准备再加一条规则时，有人说：这和前两个是同一个 bug。

## 为什么是同一个

Agent 收到的每个请求都经过一个路由器。路由器里有一张表，每一行是一种已知的请求类型，指向对应的处理能力：thread 消息给 thread 处理器，评审请求给文档评审，代码问题给代码搜索。表里没有的，全部落到一个通用兜底，用模型的通用知识作答。

把三起事故对着这张表看：被吞的回复，是消息没匹配上任何一行，落到兜底，兜底无话可说。被捍卫的文档，是重评请求和评审那一行没精确匹配，落到兜底，兜底用模型记得的内容作答。编造的代码，是问法出乎表的预料，落到兜底，兜底凭空写了一段看起来合理的代码。

三个症状，同一条路。我们三次修的都是往表里加一行，让某一种说法不再掉下去。没有一次碰过它们掉进去的那个地方。

## 为什么要到第三次才看出来

每起事故都自带一个解释。吞回复像 threading 问题，捍卫文档像记忆问题，编代码像模型幻觉。修的人不同，工单不同，每个修法在自己的范围里都是对的。整个流程里没有一步会问：还有什么别的事故长得像这个？

最后把三件事连起来的信号很普通：第三次的修法和前两次是同一种，往同一张表里加一行。这是该停下来问一句"这张表到底在干什么"的时候。

## 改了什么

我们没有改表，改的是兜底。

兜底现在多做三件事：

1. 说出它认为这个请求最接近哪种能力，然后问用户，而不是用通用知识直接答。
2. 请求只要涉及代码、文档或 thread，先走对应的工具。工具答"没找到"，比模型凭空答好。
3. 每次落到兜底，记下请求的形状。下一个没认出来的说法，是报表里的一行，不是一起事故。

## 修一行和修兜底，差在哪

| | 往表里加一行 | 修兜底 |
|---|---|---|
| 工作量 | 小，局部 | 中，涉及共享路径 |
| 修好的 | 这一种说法 | 所有还没见过的说法 |
| 下一次 | 一定会来，换个样子 | 一行日志 |
| 感觉 | 有进展 | 承认前两次没修到根 |

最后一行就是为什么要等到第三次。没人想重开两张已经关掉的工单。但该开还是要开。

<div class="callout">
<p><strong>经验：</strong>一次是 bug，两次可能是巧合，三次同一个形状就是模式。这时候不要再往表里加行，先说出这三次的共同点，找到没匹配的请求落在哪里，把那条路修一次。根几乎总在默认路径、兜底、else 分支里，也就是特例让你不去看的地方。</p>
