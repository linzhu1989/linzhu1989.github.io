## 今天早上的一件小事

今天早上我开了一个新的 Claude Code 会话，准备写这篇文章。它动手之前先跑了一次 `git status`，结果发现仓库里已经有两处改动：车辆保养那个文件夹里删掉了一个 Excel 临时锁文件，根目录下多了一个没纳入版本管理的新文件。这两处都不是这个会话改的，是别的会话之前留下的。

要是放在一个月前，这就是个隐患。一个会话干完自己的活，顺手 `git add -A`，别人改了一半的东西就跟着进了一个叫"blog: new post"的提交。

## 仓库是什么样的

这是我的个人仓库，一个文件夹里放了十来个主题：博客、家里的各种文件、整理照片、一个业余项目的上线清单。每个主题一个子文件夹，里面有一份 `notes.md`。最上面有一个 `INDEX.md`，每个主题占一行。整个仓库同步到一个私有远程仓库做备份。

我平时会同时开两三个会话，一个会话管一个主题。比如一个窗口在跑很久的照片整理，另一个窗口我在写东西。有时候昨天的会话还开在某个终端标签里，忘了关。

## 我原来以为会话之间会互相注意到

一开始我觉得不用管。这些会话能力都不差，会读文件，也会跑 `git status`，看到别人的改动应该会绕开吧。

实际上不会，而且跟能力无关。每个会话只知道自己这段对话和磁盘上的文件，根本不知道还有另一段对话存在。别的会话做的事，在它眼里就是工作区里一处来路不明的改动。Agent 又总是想把活干完，碰到来路不明的改动，多半会一起提交，或者顺手"清理"掉。

既然会话之间唯一共享的是文件，那协调的规则也只能放在文件里。

## 现在每个会话都按这套流程走

规则写在仓库的 `CLAUDE.md` 里，每个会话启动时都会自动读到。整个流程分开始、进行中、结束三段。

<figure>
<a href="/img/two-sessions/lifecycle.zh.svg" target="_blank" rel="noopener"><img src="/img/two-sessions/lifecycle.zh.svg" alt="一个会话的三个阶段。开始：带 autostash 拉取，读 INDEX，认领主题并立刻 push。进行中：只改自己的文件夹，小步提交，只 stage 自己的路径。结束：写交接说明，释放认领，push，确认没有未推送的提交。"></a>
<figcaption>开始、进行中、结束。每一步都会在 git 里留下痕迹，别的会话看得到。</figcaption>
</figure>

**开始。** 先 `git pull --rebase --autostash`。只用 `pull --rebase` 不行，只要工作区里有别人没提交的改动，它就拒绝执行，而工作区里通常都有。然后读 `INDEX.md`，找到要做的主题，把它的状态改成 `🔄 进行中（在做什么，几点开始）`。这一行改完马上单独提交、push，然后才开始干活。认领其实就是一把锁，别的会话看得到才有用。

如果这个主题已经被认领，而且认领时间不到 24 小时，会话就停下来告诉我。超过 24 小时，基本是我忘了关的旧会话，直接清掉就行。

**进行中。** 只改自己主题的文件夹，`INDEX.md` 里也只改自己那一行。到了自然的节点就提交一次，不要攒到最后一起提交。永远不用 `git add -A`：先看 `git status`，把自己的路径一个个写出来再 stage。看到自己文件夹以外有改动，不碰，跟我说一声。今天早上就是这样，会话把那两处改动列出来，说明不是它改的，然后接着干自己的活。

**结束。** 在这个主题的 `notes.md` 里写一段"下次从这里继续"，把 `INDEX.md` 里的认领换成真实状态。然后提交、拉取、push，最后用 `git status -sb` 确认本地没有没推上去的提交。任何情况下都不 force-push。

## 改了以后有什么不同

<figure>
<a href="/img/two-sessions/before-after.zh.svg" target="_blank" rel="noopener"><img src="/img/two-sessions/before-after.zh.svg" alt="之前：两个会话改同一个工作区，其中一个 git add -A，把另一个改了一半的东西一起提交了。之后：每个会话先认领主题，只提交自己的文件夹，别人的改动原样留着。"></a>
<figcaption>第二个会话不需要知道第一个会话在不在，只要不越过自己的那一块就行。</figcaption>
</figure>

| | 之前 | 之后 |
|---|---|---|
| 怎么知道某个主题有人在做 | 不知道 | `INDEX.md` 里有一行已经 push 的 🔄 |
| 提交什么 | 工作区里的所有改动 | 只提交自己的路径，逐个写出来 |
| 别人留下的改动 | 一起提交，或者被"清理"掉 | 不碰，告诉我 |
| 第二天接着做 | 从头看一遍，重新理思路 | 直接看"下次从这里继续" |
| 最坏情况 | 提交里混进别人的东西，甚至 force-push | 一条过期的认领，24 小时后清掉 |

这些规矩其实不新鲜，一个团队共用一个仓库本来就是这么做的：说一声自己在改什么，不提交别人的文件，走之前留个说明。区别在于，团队里很多事是靠开口说的，在群里说，在站会上说。会话之间没有这样的渠道，它们只会在启动时读文件，所以需要它们知道的事，都得写进文件里。

后来发现，交接说明跟认领锁一样重要。新开的会话不记得昨天发生过什么。有了"下次从这里继续"那一段，它一分钟就能接上，不用再去翻提交记录把来龙去脉重新理一遍。

<div class="callout">
<p><strong>经验：</strong>多个 Agent 并行干活，靠的是它们都会读的那些文件，不能指望它们自己机灵。认领、提交范围、交接说明都写进仓库；先 push 认领再动手；不是自己改的东西，一律当成别人的。</p>
</div>
