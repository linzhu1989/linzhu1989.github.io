## 事情经过

我在试一个 Agent 技能的新批量模式。这个技能做的是营销邮件的端到端测试：每个用例先在测试环境里订一张真实的预订，写入几条客户行为数据，触发邮件，等邮件到了再去邮箱里检查内容。单个用例的版本已经用了一段时间。批量模式从一张表格读用例，表里 72 行，其中 48 行能对应上配置，第一次我只让它跑两行。

第一轮很顺利。Agent 先给了一份范围摘要：72 行里跑 2 行，48 行有对应配置，24 行跳过并写明原因，用哪个邮箱，哪些工具可用。然后它停下来等我确认。我回了「开始」。

它做了预检，建好了批次文件夹，处理了两行用例，选好了邮件文案。到了要创建第一张预订之前，它停下来问：

> 批量输入里 `language` 默认是空的，但这几个用例之前每次成功的单独运行都是用 `es` 订的。创建预订和触发邮件都不能安全地重来。这次用什么语言？

我回答「两行都用 es」。后面一切正常：两张预订，两封邮件，一份汇总。结果挺好，我差点就这么过去了。

## 问题在哪

我原来把那句「开始」当成了对整个任务的批准。摘要就是确认点，我点了头，后面的事就都算批准过了。

可摘要里根本没有语言这一项。没人要求它列出来，所以屏幕上没有，所以我批准的其实是一个留着空白的任务。Agent 发现了这个空白，这是它做得好的地方。但它是在任务进行到一半才发现的：前面四步准备工作已经做完，后面马上就是第一个做了就撤不回的步骤。它要是稍微大意一点，就会用错的语言订两张预订，发出两封收不回来的邮件。

Agent 在最后关头谨慎了一下，这算是额外的运气，不能当成设计的一部分。

## 还有一件小事

同一次运行里，Agent 还主动交代了一件事：在出范围摘要之前，它自己用 `head` 看了一眼那张表格。按设计，用户的输入文件只能由脚本读，Agent 只看脚本算出来的结果。

这听起来有点较真，其实不是。摘要上的数字（72、48、24、2）是我要确认的东西。如果 Agent 先自己看了文件，摘要里就混进了两种来源：一部分是脚本算的，一部分是 Agent 看了前十行之后的印象。我希望我确认的内容只有一个来源。

## 怎么改的

技能说明里加了两句话，分别对应上面这两件事。

**不能重来的步骤要用到的输入，都在摘要之前定下来。** `language` 现在是批量输入的一项。Agent 要么从用户的请求里拿，要么从这几个用例以前成功的运行记录里推出来，然后把值写在范围摘要上。实在定不了，就在摘要那一步问，那时候什么都还没做。

**用户的输入文件只由脚本读，Agent 不读。** 生成计划的那一步是唯一读表格的地方，Agent 只说计划返回了什么。

## 对比

| | 之前 | 之后 |
|---|---|---|
| 问题在哪一步出现 | 任务进行中，第一张预订之前 | 范围摘要上，「开始」之前 |
| 「开始」批准了什么 | 一个有空白输入的任务 | 不可逆步骤要用的每一个值 |
| 摘要里的数字从哪来 | 计划脚本，加上 Agent 自己看的一眼 | 只来自计划脚本 |
| 如果 Agent 没那么谨慎 | 两张订错的预订，两封发出去的邮件 | 不需要它谨慎 |

## 经验

做实事的 Agent，总有几个步骤做了就撤不回来。这次是「创建预订」和「触发邮件」。在它们之前的步骤，重跑一遍不花什么成本；在它们之后的步骤，都依赖它们的结果。

所以我现在看一个新技能，会倒着看：先找出不能重来的步骤，列出它们要用的所有输入，再检查人说「开始」的那一刻，这些输入是不是每一个都显示在屏幕上。缺了哪个，那里就该有一个提问，而且这个提问应该放在摘要里，不要等到最后关头。

这次试跑一共四轮，花了 7.02 美元。Agent 停下来提问的那一轮大约一美元。它带来的两句规则，以后每一次批量运行都会用上。
