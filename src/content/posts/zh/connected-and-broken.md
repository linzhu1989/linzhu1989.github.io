## 那天发生了什么

那天早上五点，我们用的 Jira 换了域名。这是厂商统一给所有客户做的，提前也通知过。九点多一测，Slack 机器人读的操作都还正常：能搜工单、能加评论、能改状态。只有新建和修改不行，根据调的工具不同，返回 500 或者 302。

上午把各处的 URL 改成新域名以后，wiki 那边先恢复了。Jira 这边报错变了，写操作开始返回 400 和 404，看起来完全像是权限问题。可是我们自己能看到的地方全都显示正常：集成平台的连接页面写着 **已连接**，任务记录里每一次失败的新建都显示 **成功**。

## 问题在哪

我们一开始默认这些状态都是可信的：已连接，说明凭证没问题；成功，说明工单建好了；404 是东西不存在，400 是请求体写错了。于是整个上午后半段都在查请求体和字段权限。

结果这几个判断全错了，而且各错各的。

<figure>
<a href="/img/connected/layers.zh.svg" target="_blank" rel="noopener"><img src="/img/connected/layers.zh.svg" alt="一次新建请求经过四层。连接页面显示已连接，因为它只检查凭证有没有存。Jira 返回 400 或 404，因为凭证不对时会被当成匿名用户。任务显示成功，因为流程忽略了 HTTP 错误。真实情况只有最后一条：工单没建出来。"></a>
<figcaption>每一层报的都是绿色或者看似合理的结果，只有"工单不存在"这件事是真的。</figcaption>
</figure>

**"已连接"只检查凭证存没存**，不检查 Jira 认不认。存着的那份 Basic auth 凭证，已经跟新站点对不上了。

**400 和 404 其实是认证失败。** Jira Cloud 碰到错误的 Basic auth 凭证，不会直接报 401，而是把请求当成匿名用户处理。匿名用户看不到这个项目，所以请求就像是项目或者字段不存在一样失败了。唯一的线索在响应头里：`x-seraph-loginreason: AUTHENTICATED_FAILED`。

**"成功"是我们自己造成的。** 这些集成流程当初配的时候设置了忽略 HTTP 错误，不管返回什么，包括 400，任务都按成功结束。所以任务记录记下的只是"调用发出去了"，不是"工单建好了"。

## 怎么查出来的

最后起作用的是一个很笨的办法。我用完全相同的 URL、相同的请求体，只把共享凭证换成我自己的 API token，再发一次，第一次就建成了。这一下就排除了请求体、URL 和字段映射，剩下的只可能是凭证。下午凭证修好以后，原来的流程一行没改，指向新域名就全好了。中间我们还在另一种连接方式上搭了一套备用流程，最后没用上，一直关着。

## 另一个服务，一整天悄悄失败

当天晚上我们排查了一遍，还有哪些地方指着旧域名。一个造测试数据的服务就是。它的 Jira 客户端在配置里写的还是旧地址，而旧域名现在对所有路径都返回 302，跳到新域名。

<figure>
<a href="/img/connected/redirect.zh.svg" target="_blank" rel="noopener"><img src="/img/connected/redirect.zh.svg" alt="对旧域名发 GET，收到 302，客户端默认会跟着跳到新域名。发 POST 或 PUT，收到同样的 302，但客户端默认不会跟着跳，写操作根本到不了新域名。"></a>
<figcaption>同一个 302，读和写的处理方式不一样：读会跟着跳，写到这里就停了。</figcaption>
</figure>

HTTP 客户端碰到 GET 的跳转，一般会自动跟过去。POST 和 PUT 通常不会，因为把一个写请求替你重新发到另一个地址，并不安全。所以这个服务的搜索、更新、关联工单，很可能从早上五点起就一直在失败，只是没有任何地方报警，谁都没发现。修起来就是改一行配置再部署一次。部署到 staging 以后，之前一直返回 500 的接口变成了 200。

## 对比

| | 显示的是什么 | 实际意思 |
|---|---|---|
| 连接页面 | 已连接 | 凭证存着 |
| 任务记录 | 成功 | 调用返回了，不管返回什么 |
| Jira 返回 400 / 404 | 请求错误、找不到 | 你被当成匿名用户了，先查认证 |
| 旧域名上的 GET | 跳转后 200 | 暂时没事 |
| 旧域名上的 POST / PUT | 302 | 写请求根本没到 |

## 经验

那天以后我们改了三件事。第一，集成流程遇到 4xx 和 5xx 要报错，新建失败就该显示成失败的任务。第二，连接有任何改动，都用一次真实的写操作验证，再把结果读回来看，点一下"测试连接"不算。第三，域名一变，要把所有服务的配置都搜一遍旧地址，不能只修报错最响的那一个。不出声的那些，往往到半夜还在失败。

<div class="callout">
<p><strong>经验：</strong>绿色的状态只能说明状态本身。要确认连接能用，就让它真正写一次，再去看结果在不在。错误要让它以错误的样子暴露出来；查不出原因的时候，保持其他条件不变，一次只换一个变量，比如凭证。</p>
