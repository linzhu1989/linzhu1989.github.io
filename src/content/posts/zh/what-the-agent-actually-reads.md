## 一张空工单

一个 Agent 创建了一张工单，描述字段是空的。指令里写得很清楚：描述必填，内容是什么。工单平台也没有丢字段。我们查了请求，Agent 根本没有发描述这个字段。

原因是这样的。"创建工单"这个工具的定义里，描述字段标的是可选。说描述必填的那条规则，写在一个只有做某类任务时才加载的指令文件里，这次不是那类任务，文件没加载。Agent 面前有两段文字，一段说可选，一段它根本没看到。它照可选做了。

修法是改工具描述里的一句话，把描述改成必填并说明要写什么。没有在指令文件里再加规则。

## 工具描述是 Agent 一定会读的那段文字

给 Agent 接工具，很容易把它当成接线的活：起个名，写个 Schema，把调用转发过去，完了。这篇里的每个 bug 都来自这个想法。

工具定义有一个特殊之处：只要工具在列表里，Agent 每次调用前都会读它的描述。指令文件不一样，只有加载了才会被读。两边内容冲突的时候，Agent 一定按工具描述做，因为那是它眼前的东西。

所以我们定了一条规则：什么字段必填、什么时候该调用这个工具，写在工具自己的描述里。指令文件负责补充判断，不单独持有任何一条硬规则。

## 工具返回空的时候

工具出错，多数时候不是返回错误，而是返回一个看起来正常的空。

一个搜索工具对某个概念返回零结果，领域专家坚持这东西存在。我们先猜是模型幻觉，又猜是别的 thread 混进了上下文。真正的原因是这个工具把两个词的查询当成"两个词必须在同一行"，把整个子系统都过滤掉了。没有报错，就是零。

另一个工具声明返回工单，多数时候确实返回工单，偶尔返回一个只有 key 的空对象。Agent 拿着这个空对象当工单继续推理。

从这两件事定了两条规则。第一，工具返回空不能当作"不存在"：对话里 Agent 要说明它搜了什么，定时任务里空结果直接算错误。第二，写入之后一定读回来逐字段对比，写入工具说"成功"只是它的说法，不是事实。

## 工具的名字

名字听起来最不重要，但正是名字这里，指令和现实最容易悄悄分开。

我们的工具通过一个网关访问共享系统，网关会把工具名统一：上游平台叫 `get_issue_Jira_`，Agent 看到的是 `jira_get_issue`。这本身合理。问题是，按上游名字写的指令，指向的是一个从 Agent 视角看不存在的工具。Agent 遇到这种情况会做三件事之一：选一个名字最像的，解释说做不了，或者做一件差不多的事。三种都发生过。

规则：工具名对着 Agent 实际看到的列表核对，不对着上游文档。动词加名词，从 Agent 的角度命名，所有指令里用同一个名字。

## 工具的鉴权

一次安全评审发现两个内部工具网关没有任何入口鉴权。能访问到地址的人，就能用网关自己的凭据调后面任何工具。当时还没出事，但没出事不等于安全。

修法是在网关鉴权一次，后面的工具继承调用者的身份，其他地方不用再登录。这件事还带出一个之前没问过的问题：一次错误的调用能影响多大范围？读工具可以给宽一些，写工具要窄，一个工具只做一个动作，删除、发送、付款这类危险动作要先问，或者先写草稿。

## 检查清单

| 检查项 | 怎么检查 | 出问题的表现 |
|---|---|---|
| 名字 | 动词加名词，从 Agent 视角，所有指令里一致 | Agent 调一个不存在的工具，或最像的那个 |
| 什么时候用 | 写在描述里了吗 | 选错工具 |
| 必填字段 | Schema 的 required 和真实规则一致吗 | 字段悄悄为空 |
| 返回空 | 描述说明了"没找到"是什么意思吗 | 从零结果得出自信的答案 |
| 写入校验 | 写完有没有读回来 | 显示成功，实际记录是错的 |
| 鉴权 | 调用者在网关被识别了吗 | 网络上任何人都能调 |
| 影响范围 | 读宽写窄，危险动作先问 | 一次错误调用，一大堆后果 |

这张表里没有一行是关于模型的，全是关于我们放在模型面前的文字和边界。
