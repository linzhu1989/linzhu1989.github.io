## 背景

我负责一个内部服务，用得最多的是一张创建测试数据的表单。QA、开发、产品经理都用它做 demo、开发、测试。填这张表要先选一个 partner，再填十几个字段，每个字段能填什么取决于这个 partner 支持什么：产品、货币、语言，还有一堆特殊规则。没人记得全，包括做这个服务的我自己。

结果就是反复出现同一个循环：有人填错，看到一个看不懂的报错，来问我们，我们查完回复，他再去试。一行测试数据，两边各花半天。

## 二月：加了个聊天面板

二月我在表单旁边加了个聊天面板。选好 partner 之后，用户可以说"随便来一个"，或者用一句话描述需求，面板帮他把表填好。前端 React，后端 Spring Boot，模型是 Claude，通过 Bedrock API 调用。从第一个 commit 到第三版原型，五周。

当时我以为自己在做的是一个聊天机器人，价值在对话：把"我要一个两人、带中转的预订"翻译成十四个字段。现在回头看，早期做的两个设计比对话本身重要得多。

第一个设计：模型不负责事实。分工从一开始就定了，模型只做语言理解，业务事实全部由代码回答。这个 partner 支持哪些货币、哪些产品、选了 cruise 之后哪些字段必填，这些问题的答案来自读服务和缓存的普通代码，以几个函数的形式暴露给模型，模型需要时调用。函数里没有模型。当时我不知道这个模式叫什么，代码里就叫它们 tools。

第二个设计：知识放在文件里。prompt、partner 备注、字段说明、按钮直接触发不经过模型的特殊流程，全是 YAML，启动时加载，用占位符注入 prompt。当时的动机是让代码干净，让非开发也能改措辞。后来没有第二个人改过，但这个结构一直留着。

还有一个当时没想到的点：我一开始不知道模型两次调用之间不保留任何东西，是看到它"忘事"才发现的。解决办法是前端保存整段对话，每轮回传，后端每次从零重建 prompt。后来文档里写的是 stateless by design，实际是踩了坑才这么设计的。不过效果是好的：没有东西要持久化，重启不丢数据，每个请求可以单独测。

用的人不少。我们遇到的准确率问题，几乎没有一次是模型的问题。建议错的时候，错的是给模型的信息：某个 partner 的数据缺了，两个 partner 在一段对话里混在一起，或者事实在 prompt 里的排法让模型读错了。

## 三月：拆成 MCP server

三月情况变了。公司开始推终端里的编码助手，原来打开网页的人，现在大部分时间待在一个自带模型的 CLI 里。网页表单里的聊天面板，看起来像第二个、更差的聊天窗口。

问题就变得很明显：知识为什么要锁在我的 UI 后面？工具本来就是普通函数，partner 事实、字段规则、特殊流程本来就是文本，这些都可以直接交给任何会说通用协议的助手。

于是我们在同一个服务上加了一个 MCP server，两周出了 PoC。聊天面板一直在调的那些函数变成 MCP 工具，YAML 里的知识变成工具描述和助手动手前先读的说明。聊天面板原样保留，变成了众多客户端中的一个。

这一步的难点不在协议。难点是同事用三种不同的客户端，每种配置格式都不一样，而且大多数人对这些都不熟。安装必须是一条命令，否则推广会卡在 README 上。最后做成了一条命令。

半年后，这个 server 暴露几十个工具，创建测试数据只是其中一类。我后来在别的 runtime 上做的 Agent，也都通过它访问测试系统。聊天面板还在，还有多少人用，我没有查过。

## 对比

| | 聊天面板 | MCP server |
|---|---|---|
| 入口 | 一个网页 | 任何会说 MCP 的助手 |
| 对话由谁管 | 我的代码 | 用户本来就在用的助手 |
| 我要维护什么 | UI、prompt 组装、对话状态、工具、知识 | 工具、知识 |
| 加一个能力 | 面板里加一个流程 | 加一个工具，用文字描述 |
| 建造时间 | 五周 | 两周，在前者基础上 |

第三行是重点。面板要我维护五样东西，server 只要两样，而这两样恰好是我最先做的，因为它们是唯一不需要模型就能测试的部分。

<div class="callout">
<p><strong>经验：</strong>做 AI 功能的时候，先找出那些没有模型也成立的部分：事实、规则、动作。把它们做成普通函数和普通文本。聊天界面只是一个客户端，客户端会换，函数和文本会留下来。</p>
</div>
